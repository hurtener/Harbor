# Harbor TUI Research: Scope And Product Boundary

## Decision Frame

This investigation targets a **generic Harbor runtime test and control TUI**.
It is not a coding agent, an IDE, or the proposed future HarborCode product.

The TUI should optionally accompany:

- the stock `harbor serve` Protocol server;
- an agent binary generated by `harbor scaffold --with-server`; and
- a remote Harbor Protocol endpoint.

In every mode, the TUI remains a Harbor Protocol client. It must not read
Runtime internals, bypass authentication, or introduce a second source of
truth for sessions, tasks, events, artifacts, tools, memory, or pauses.

## Product Job

The first product job is deliberately narrow:

> Let an agent author or operator attach to a Harbor Runtime, exercise an
> agent interactively, observe exactly what the Protocol exposes, intervene
> safely, and diagnose the resulting task without opening the web Console.

The useful OpenCode precedent is its interaction quality, not its coding
domain. Harbor should inherit the following qualities:

- immediate launch into a focused composer;
- resilient streamed output;
- typed, ordered visual blocks instead of raw log lines;
- keyboard-first command discovery;
- session switching and resumability;
- visible pending permissions, questions, and failures;
- compact but information-rich status surfaces;
- local prompt history, drafts, frecency, and preferences;
- responsive layouts that remain usable in a narrow terminal;
- polished themes and predictable visual rhythm; and
- one client architecture for local and remote attachment.

## In Scope

### Core Interaction

- Connect to a Runtime and verify Protocol compatibility.
- Create, hydrate, rename, and erase Harbor sessions. `start` reactivates a
  closed non-erased session and emits `session.reopened`; an erased ID is
  terminal and returns `session_erased` rather than silently creating a new
  conversation.
- Submit text and artifact-backed turns.
- Stream answer and reasoning output.
- Inspect tool lifecycle, planner decisions, task status, cost, and errors.
- Cancel, pause, resume, redirect, inject context, prioritize, approve,
  reject, and send a user message to a live run.
- Reconcile pending pauses and approvals after reconnect.
- Apply one-shot run overrides that the Protocol supports.
- Export a locally rendered transcript.

### Runtime Inspection

- Runtime health, scoped retention horizons, version, capabilities, drivers,
  metrics, LLM posture, and governance posture.
- Tasks and parent/child task relationships.
- Tools and their manifests, schemas, policy, metrics, and OAuth posture.
  Rich annotations are gated by `tool_annotations`; bounded analytics remain
  best-effort because their wire rows do not yet expose scan truncation.
- Artifacts and multimodal input disposition.
- Memory entries and strategy traces.
- MCP server status and metadata, with terminal-appropriate degradation for
  MCP Apps.
- Raw event stream, durable event history, dropped-event diagnostics, and
  filtered event views.
- Agent metadata and configuration where authorized.
- Flows and topology only when the attached Runtime advertises them.

### TUI-Local State

- Recent connections, never bearer-token plaintext by default.
- Keybinding overrides.
- Theme and display preferences.
- Prompt history, draft stash, attachment history, and frecency.
- A clearly labelled client-local follow-up queue until Harbor owns a durable
  pending-turn primitive.

## Explicitly Out Of Scope

The following OpenCode features are coding-agent surfaces and do not belong in
this product:

- repository file tree;
- Git status, branch, patch, and source-diff viewers;
- LSP diagnostics, symbol search, formatter status, or language detection;
- shell/PTY terminal;
- source editing, external-editor integration, or code concealment;
- file-system `@` completion as the primary attachment model;
- worktrees and coding workspaces;
- code-specific read, grep, glob, edit, write, or patch cards; and
- any implied HarborCode agent, agent prompt, planner, or tool suite.

These may inform future extension points, but they must not shape the first
TUI's Protocol requirements or navigation.

## Architectural Invariants

1. **The Runtime remains headless.** Optional co-launch is CLI composition,
   not a Runtime dependency on UI code.
2. **The TUI is a Protocol client.** Local and remote modes exercise the same
   HTTP plus SSE surface.
3. **Identity remains mandatory.** Loopback is not an authentication bypass.
4. **The identity triple remains visible and isolated.** Every connection,
   session switch, event subscription, and destructive action carries the
   attached `(tenant, user, session)` context.
5. **No Console shadow database.** TUI-local storage contains interaction
   preferences and drafts only.
6. **Planner neutrality.** The UI renders canonical task, event, pause, tool,
   and artifact projections; it must not assume a ReAct planner.
7. **Unknowns degrade visibly.** Unsupported methods, unknown event types,
   and unknown tool/result shapes render generically rather than disappearing.
8. **Heavy content remains artifact-backed.** The TUI must not encourage raw
   heavy payloads to cross Harbor's context safety boundaries.

## Optional Launch Posture

The preferred user-facing modes are:

```text
harbor tui --attach https://runtime.example --token-file ...
harbor serve --tui --config harbor.yaml
./my-agent --tui --config harbor.yaml
```

The second and third forms are conveniences around one client:

1. boot the existing Protocol server;
2. wait until its actual bound address is ready;
3. launch the TUI against that address with normal Protocol credentials;
4. keep server and TUI shutdown semantics explicit; and
5. never expose internal handles to the TUI.

`harbor serve` and `sdk/server` are production-only and mint no token. A
co-launched TUI therefore needs a JWT accepted by the configured JWKS, just
like a remote client. Local setup remains `harbor token keygen` followed by
`harbor token mint`, or an external identity provider.

## First Release Screen Set

1. **Connect**: URL, credential source, identity, Protocol compatibility,
   health, and event-stream state.
2. **Conversation**: composer, ordered stream, attachments, run controls,
   reasoning, tool lifecycle, result, cost, and errors.
3. **Sessions**: new, list, search, switch, rename, inspect, and erase.
   Closed sessions offer Resume through `start`; erased sessions offer a clear
   Start Fresh remediation using a new ID.
4. **Interventions**: pause snapshot, approval/rejection, OAuth hand-off, and
   operator questions.
5. **Tasks**: foreground/background tasks, progress, parent/child links,
   result, trajectory, cost, and failure details.
6. **Tools**: catalog, schemas, policy, metrics, and connection posture.
7. **Events**: filtered live stream, history, reconnect, and drop diagnostics.
8. **Artifacts**: upload, metadata, references, and external-open where the
   backing store supports retrieval.

Memory, MCP administration, agent configuration, flows, and topology are
advanced screens. They should use the same command palette and dialog
primitives without crowding the initial conversation experience.

## Research Rule

OpenCode findings in the rest of this directory use two classifications:

- **Reusable interaction pattern**: suitable for the generic Harbor TUI.
- **Deferred coding-specific reference**: retained only for possible future
  HarborCode analysis.

When those classifications conflict, this document wins.
